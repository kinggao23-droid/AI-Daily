## 1. 今日要闻

### 🔥 要闻一: Google Cloud Next '26 发布 Gemini Enterprise Agent Platform — Vertex AI 正式转型为 Agent 平台

**平台**: Google Cloud / Vertex AI  |  **时间**: 2026-04-24 (Google Cloud Next '26)

**具体更新内容**:
- Google 宣布 Gemini Enterprise Agent Platform, 作为 Vertex AI 的正式进化方向。未来所有 Vertex AI 新功能均将通过 Agent Platform 交付
- 平台整合六大核心模块: Agent Studio (可视化 Agent 构建)、Agent-to-Agent Orchestration (多 Agent 编排)、Agent Registry (Agent 注册中心)、Agent Identity (Agent 身份认证)、Agent Gateway (API 网关)、Agent Observability (Agent 可观测)
- Model Garden 扩展至 200+ 模型, 涵盖 Gemini 3.1 Pro、Gemini 3.1 Flash Image、Lyria 3, 以及 Gemma 4、Claude Opus/Sonnet/Haiku 等第三方模型
- 新增 Gemini Enterprise 应用: Agent Designer (自然语言定义 Agent)、Inbox (管理 Agent 活动)、长时运行 Agent、Skills (自然语言自动化工作流)、Projects
- Google 同步宣布 7.5 亿美元 AI Agent 合作伙伴创新基金, 鼓励合作伙伴构建行业 Agent
- Gemini 3 Flash 进入公测, 定位复杂多模态推理和编程; Gemini 3.1 Flash-Lite 公测, 主打低延迟高性价比

**设计理念解读 (为什么这么做)**:
- Google 的核心判断: 企业 AI 市场正从"聊天助手"转向"能执行多步骤任务的 Agent 系统"。将 Vertex AI 重新定位为 Agent Platform, 是抢占"Agentic 时代"平台入口的战略选择
- Agent-to-Agent Orchestration 反映了一个趋势: 企业不再只需要单个 Agent, 而是需要多个 Agent 协作完成复杂业务流程
- 7.5 亿美元基金的目的是快速培育 Agent 应用生态, 弥补 Google 在企业应用层的短板 (相比 Microsoft 的 Copilot 生态)
- 200+ 模型的 Model Garden 延续了"不绑定单一模型"的策略, 但自家 Gemini 始终是默认推荐

**代差对比 (历史视角)**:
- 上一代怎么做: Vertex AI 2024 年是"模型服务 + RAG + 微调"的传统 MLOps 平台, Agent 能力局限于 Vertex AI Agent Builder 的简单对话 Agent
- 这一代代差关键: 从"模型平台"升级为"Agent 全生命周期平台" — 涵盖构建、编排、注册、身份管理、网关、可观测六层能力, 形成完整的 Agent 基础设施栈
- 类比相似的历史演化: 类似 VMware 从"虚拟机管理"转型为"云原生应用平台" (Tanzu), 底层能力不变但产品定位完全重塑

**影响分析 (跨行业)**:
- 对国内厂商的启示: "Agent Platform"正在成为云厂商的标准产品形态。Google 的六层架构 (Studio/Orchestration/Registry/Identity/Gateway/Observability) 可作为 LLMOps 平台的能力对标清单
- 对金融客户落地: 不可直接使用 (数据出境); 但 Agent Registry + Agent Identity 机制对金融行业 Agent 权限管控有直接参考价值
- 对泛政府客户落地: 不可直接使用; 但 Agent-to-Agent Orchestration 对政务"一网通办"跨部门协作 Agent 有架构参考意义
- 对国央企客户落地: 不可直接使用; 但 Agent Gateway 的统一入口 + 流量管控 + 安全策略模式适合国央企集团级 Agent 管理

### 🔥 要闻二: Databricks 发布 Agent Bricks + Unity AI Gateway — 数据湖仓平台全面拥抱 Agent 治理

**平台**: Databricks  |  **时间**: 2026-04 (多项更新集中发布)

**具体更新内容**:
- Agent Bricks 平台发布: 统一构建、部署和治理生产级 AI Agent 的端到端平台, 结合模型访问、Lakehouse 数据上下文、Unity Catalog 身份治理和自动化评估
- AI Gateway 升级为 Unity AI Gateway, 并入 Unity Catalog 统一治理体系:
  - 细粒度权限控制: 精确管理 Agent 对 LLM 和 MCP 服务器的访问权限, 支持代理访问 (OBO)
  - 端到端可观测: 监控 LLM 和 MCP 调用链路, 按模型/团队/工作流归因成本
  - 统一模型 API: 跨模型统一调用接口, 内置 fallback、速率限制和 guardrails
- 新增模型: OpenAI GPT-5.5 和 GPT-5.5 Pro 以 Databricks 托管模型上架, Claude Opus 4.7 同步上线
- Supervisor Agent SDK: 支持用 Databricks Python SDK 创建多级 Agent (Supervisor + 子 Agent), 可将自定义 MCP 服务器和 Databricks Apps 作为子 Agent 接入

**设计理念解读 (为什么这么做)**:
- Databricks 的核心逻辑: "谁拥有数据, 谁就应该拥有 Agent 的治理权"。将 AI Gateway 并入 Unity Catalog, 意味着 Agent 的权限、审计、成本管控与数据治理共用一套体系, 降低企业管理复杂度
- Agent Bricks 的定位不是与 LangChain 竞争 Agent 框架, 而是提供"Agent 的运行平台" — 框架在上面跑, Databricks 管数据和治理
- Supervisor Agent 的多级架构反映了企业 Agent 系统的真实需求: 一个"主管 Agent"协调多个"专业 Agent", 各司其职

**代差对比 (历史视角)**:
- 上一代怎么做: Databricks AI Gateway (2024) 是简单的 API 代理层, 仅做模型路由和速率限制, 治理能力有限
- 这一代代差关键: 从"API 代理"升级为"统一治理层" — 权限/审计/成本/可观测全部纳入 Unity Catalog, 与数据治理深度打通
- 类比相似的历史演化: 类似 Kubernetes 从"容器编排"到"服务网格 (Istio)"的演进 — 不仅管"跑什么", 还管"谁能访问、怎么访问、花了多少钱"

**影响分析 (跨行业)**:
- 对国内厂商的启示: "Agent 治理纳入数据治理体系"是一个高价值产品方向。数据平台厂商天然拥有企业数据权限和审计基础, 在此之上构建 Agent 治理层成本最低、效果最好
- 对金融客户落地: 高度相关 — Unity AI Gateway 的 OBO 权限模型和成本归因能力直接匹配金融行业的合规审计需求
- 对国央企客户落地: 高度相关 — 集团级多 Agent 管理、跨部门成本分摊是国央企的刚需, Supervisor Agent 的多级架构适合集团-子公司的组织结构

### 重点功能深度解读

**功能一: Google Gemini Enterprise Agent Platform 六层架构**

- 是什么: 将 Agent 开发的完整生命周期拆分为六个独立但协同的层次 — 构建 (Studio)、编排 (Orchestration)、注册 (Registry)、身份 (Identity)、网关 (Gateway)、可观测 (Observability), 每层独立演进但统一管控
- 落地难度: ⭐⭐⭐⭐ (完整复刻需要大量平台工程投入, 但可分层逐步实现)
- 业务价值: ⭐⭐⭐⭐⭐ (为企业提供了从 Agent 原型到生产的完整路径, 解决了"Agent 能 Demo 但上不了线"的痛点)
- 最适合的行业场景: 金融 — 多 Agent 协作的智能投顾/风控审批; 国央企 — 集团级 Agent 注册中心统一管理各子公司 Agent
- 建议: **建议将六层架构作为 LLMOps 产品路线图的参考框架**。短期优先实现 Gateway + Observability (门槛低、价值高), 中期补齐 Registry + Identity (管控层), 长期实现 Studio + Orchestration (创作层)

**功能二: Databricks Unity AI Gateway 的成本归因**

- 是什么: 按模型、团队、工作流三个维度实时追踪和归因 Agent 运行成本, 与 Unity Catalog 的权限体系打通, 实现"谁调用了什么模型、花了多少钱"的全链路审计
- 落地难度: ⭐⭐⭐ (需要打通计费系统和权限系统, 数据平台厂商有天然优势)
- 业务价值: ⭐⭐⭐⭐⭐ (企业 Agent 规模化后, 成本管控是第一大运营难题; 没有成本归因, CFO 不会批预算)
- 最适合的行业场景: 金融 — 按业务线计费; 国央企 — 按子公司/部门分摊
- 建议: **强烈建议纳入 Roadmap**。成本归因是企业 Agent 从"实验"转"生产"的关键前提, 产品经理应优先设计"按组织/项目/模型"三维度的成本看板

**功能三: vLLM v0.18-v0.20 快速迭代的技术要点**

- v0.18.0: gRPC 服务端 (--grpc 标志), GPU NGram 推测解码 (speculative decoding 提速约 1.5-2x), FlexKV 缓存卸载后端
- v0.19.0: Gemma 4 全系列首日支持 (E2B/E4B/26B MoE/31B Dense), 异步调度器默认开启, Model Runner V2 引擎
- v0.20.1: Python 3.14 支持, HuggingFace Transformers v5 兼容, CVE 安全补丁
- 启示: vLLM 14 天内发 3 个版本, 说明推理引擎层的竞争极其激烈。对于自建推理的企业, 跟进 vLLM 更新是保持性能领先的必要工作。gRPC 服务端的发布意味着 vLLM 正在从"开发者工具"向"企业级推理基础设施"演进

## 4. 新兴平台雷达

### 🆕 Portkey — LLMOps AI 控制平面

- **融资**: 1500 万美元 B 轮, Elevation Capital 领投, Lightspeed 跟投
- **定位**: 企业级 AI 控制平面 (AI Control Plane), 在 LLM 与应用层之间提供统一的路由、治理、可观测和安全层
- **核心能力**: 多模型统一路由、成本管控、安全策略执行、Agent 可观测
- **值得关注的原因**: 随着企业同时使用多家模型供应商 (OpenAI + Claude + DeepSeek + 开源), 需要一个独立于云平台的"控制平面"来统一管理。Portkey 切的就是这个需求
- **参考**: [Portkey 融资新闻 (StartupNews)](https://startupnews.fyi/2026/02/20/llmops-startup-portkey-raises-15-million-in-round-led-by-elevation-capital/)

### 🆕 AMI Labs — JEPA 世界模型

- **融资**: 10.3 亿美元种子轮, 35 亿美元 Pre-money 估值
- **创始人**: Yann LeCun (原 Meta AI 首席科学家)
- **定位**: 基于 JEPA (Joint Embedding Predictive Architecture) 架构构建世界模型, 与当前主流的 Transformer LLM 路线不同
- **值得关注的原因**: 如果 JEPA 路线成功, 可能开辟与 LLM 不同的 AI 范式, 对 LLMOps 平台的架构设计产生深远影响
- **风险点**: 技术路线尚未验证, 目前仍处于研究阶段

- **融资**: 3800 万美元种子轮, 从隐身模式出来
- **定位**: 下一代企业 AI 基础设施栈
- **值得关注的原因**: 瞄准企业 AI 基础设施层, 与 Databricks、Snowflake 等数据平台的 Agent 基础设施形成竞争

## 6. 对产品经理的启示

### 启示一: "Agent Platform"已成云厂商标准产品形态, LLMOps 平台需重新定位

Google 将 Vertex AI 重定位为 Gemini Enterprise Agent Platform, AWS 推出 AgentCore + Managed Agents, Databricks 发布 Agent Bricks — 三大平台在同一个月内同时完成了从"模型服务平台"到"Agent 平台"的转型。

**建议**: 产品规划中应将"Agent 全生命周期管理"作为 LLMOps 平台的核心价值主张, 而非仅仅是"模型管理 + Prompt 工程"。Google 的六层架构 (Studio/Orchestration/Registry/Identity/Gateway/Observability) 可作为能力对标框架。

### 启示二: Agent 治理 (Governance) 已成为企业采购的前置条件

Databricks 将 AI Gateway 纳入 Unity Catalog、AWS 发布 Bedrock Guardrails 组织级策略 GA、Google 推出 Agent Identity 和 Agent Gateway — 所有平台都在强调"治理先于 Agent 能力"。

**建议**: 在产品路线图中, "Agent 权限管控 + 成本归因 + 审计追溯"的优先级应高于"Agent 构建工具"。企业客户 (尤其金融和国央企) 的采购决策链中, 安全合规部门的否决权大于业务部门的推荐权。

### 启示三: 多模型策略已成定局, "模型路由与成本优化"成为刚需功能

AWS 上架 OpenAI (打破 Azure 独占)、Azure 引入 DeepSeek V4 + Grok 4、Google Model Garden 扩至 200+ 模型 — 企业将同时使用多家模型已是确定趋势。

**建议**: LLMOps 平台必须具备智能模型路由能力 (按场景/成本/延迟自动选择最优模型) 和成本对比看板。Portkey 获 1500 万美元融资验证了"AI 控制平面"的市场需求, 这一能力应作为平台的基础模块而非增值功能。

### 启示四: 开源推理引擎 vLLM 快速迭代, 自建推理的可行性持续提升

vLLM 14 天发 3 个版本 (v0.18→v0.20), gRPC 服务端和 GPU 推测解码等企业级特性加速落地。对于有自建需求的企业 (尤其数据不出域的金融和政务客户), "开源模型 + vLLM 推理 + LLMOps 平台管理"的组合方案成本和可控性优势进一步扩大。

**建议**: 在产品方案中提供"vLLM 推理引擎集成"的选项, 支持客户在私有化环境中高效运行 DeepSeek、Qwen、Gemma 等开源模型。
